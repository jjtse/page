湖倉架構調整－中台 ETL 因應方案討論

因應既有 log_status 停止維護，彙整三種處理方式及影響，供可行性討論。

一、討論背景

目前中台 ETL 採固定排程執行；批次啟動後，會先查詢由湖倉維護的 log_status，確認當日資料已到位後，再進行資料同步及後續 ETL。

因湖倉架構調整，後續將不再維護既有 log_status，並提供 File Trigger 及 Log Center 兩種替代方式。初步評估兩種方式均需開發調整，但異動重點不同：

  • 方案 A－File Trigger：主要影響既有 Job 結構，需要配合 Trigger 拆分／調整 Job。
  • 方案 B－Log Center：既有主要 Job 可較多保留，但中台需新增服務或批次，解析 Log Center 並產出中台自己的狀態資料。

因此另外想到第三種較單純的處理方式：

方案 C：維持既有固定排程，但取消 log_status 前置檢核，排程時間到即執行資料同步及 ETL。

此方式的主要差異不是「不拉資料」，而是不再等待湖倉到檔狀態確認；資料仍會依排程同步，只是若湖倉資料較晚到，當次同步取得的可能不是最新一批資料。

二、現行流程與方案 C 差異

現行流程

固定排程啟動
→
檢查 log_status
→
確認到檔
→
同步資料／執行 ETL
重點：固定排程已存在，但需先確認湖倉到檔狀態。

方案 C 流程

固定排程啟動
→
不檢查 log_status
→
直接同步資料／執行 ETL
重點：排程機制不變，只移除到檔狀態的前置判斷。

四、方案 C－優缺點

優點

  • 異動幅度最小：不需拆分既有 Job，也不需新增狀態表及解析服務／批次。
  • 開發／測試工時較低：主要調整既有批次的 log_status 前置判斷，較有機會配合年底前完成。
  • 既有執行方式變動小：目前本來就是固定排程，方案 C 僅移除到檔檢核，不改變原有排程模式。

缺點

  • 資料同步可能有時間差：資料仍會依固定排程拉取，但湖倉下檔時間不固定；若資料在中台排程後才到檔，當次取得的不是最新一批資料。
  • 可能產生無效運算：若湖倉當下尚無新資料，中台仍會依固定排程執行 ETL。
  • 資料未更新時需額外確認來源時間：若中台 ETL 執行正常但資料未更新，需確認湖倉最新資料實際到檔時間，以判斷是否為排程與到檔時間差所致。

五、實際情境說明

情境結果
湖倉資料於中台排程前到檔 正常取得最新資料
湖倉資料於中台排程後才到檔 當次同步存在時間差；中台仍會拉取排程當下可取得的資料，需要時可沿用既有重跑機制。
湖倉當下尚無新資料 ETL 仍會執行，可能產生無效運算。

六、希望討論確認的事項

  • 資料時效性：固定排程與湖倉不固定到檔時間之間可能產生時間差，此情況是否可接受？
  • 整體取捨：若上述限制可接受，是否可考慮採用方案 C，以降低本次異動範圍及年底前的開發時程風險？
